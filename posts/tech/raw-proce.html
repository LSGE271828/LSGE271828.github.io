OpenCameraIQ：面向 RAW/ISP 的结构与噪声感知图像恢复平台

OpenCameraIQ 是一个围绕 **Camera RAW、ISP Pipeline 与图像质量分析**搭建的实验平台。

项目关注的并不是单独实现某一个图像处理算法，而是希望把 RAW 输入、Metadata 解析、图像恢复、ISP 处理、质量评价以及可视化调试串成一条完整链路。

整体流程可以概括为：

RAW / Camera Frame
        ↓
Camera Source
        ↓
RAW Metadata / Normalize
        ↓
ISP / Image Restoration
        ↓
Image Quality Metrics
        ↓
Web Tuning Console

项目工程主干采用 C++17，围绕 Camera Source → Frame → ISP Pipeline → Metrics 进行模块化设计，并通过 Web 调参台观察处理结果、图像统计和运行性能。

在此基础上，我选择了两个比较典型的 RAW 图像问题进行实验：

  • Quad-Bayer 特殊 CFA 结构恢复
  • 真实手机 RAW 噪声恢复

二者分别对应 RAW Pipeline 中两个不同的问题：

采样结构变化
    ↓
Pattern-Aware Reconstruction

真实传感器噪声
    ↓
Noise-Aware Restoration

最终统一输出为标准 Bayer RAW，再进入后续 ISP。

一、为什么从 RAW 域开始处理

常见图像算法通常直接处理 RGB 或 JPEG 图像，但对于 Camera / ISP 来说，很多问题在转换到 RGB 之前就已经发生。

Sensor 输出的 RAW 数据中仍然保留：

Bayer Pattern
Black Level
White Level
ISO
Exposure
White Balance Metadata
Color Matrix

这些信息直接决定后续 ISP 如何解释像素。

例如，同样一个像素值，在不同 ISO、曝光时间、Black Level 或 CFA Pattern 下，实际物理意义并不相同。

因此，在 RAW 域进行图像恢复时，不能简单把输入看成普通灰度图，而需要同时考虑：

  • Sensor 采样方式；
  • CFA Pattern；
  • 信号动态范围；
  • Sensor Noise；
  • Camera Metadata；
  • 后续 ISP Pipeline。

项目中已经实现 RAW/DNG Metadata 检查工具，可以读取 Bayer Pattern、Black Level、White Level、ISO、曝光以及白平衡等关键参数。

二、Quad-Bayer：特殊 CFA 结构恢复

Quad-Bayer 是手机 Camera 中比较典型的一类 CFA。

传统 Bayer 一般采用类似 RGGB 的 (2\times2) 周期结构，而 Quad-Bayer 会让多个相邻像素具有相同颜色。

这种设计可以在低照条件下通过 Pixel Binning 提高感光能力，但同时也带来一个问题：

原始 Quad-Bayer RAW 不能直接按照标准 Bayer RAW 进入普通 ISP Pipeline。

因此需要进行 Remosaic。

1. Quad CFA 采样模型

可以将 Quad-Bayer RAW 表示为：

Q(x,y)=MQ(x,y)⊙I(x,y)Q(x,y)=M_Q(x,y)\odot I(x,y) Q(x,y)=MQ​(x,y)⊙I(x,y)

其中：

  • (I(x,y))：理想连续图像；
  • (M_Q(x,y))：Quad CFA Sampling Mask；
  • (Q(x,y))：Sensor 实际采样得到的 RAW。

这里的核心问题并不是简单插值，而是：

如何根据 CFA Pattern 和局部结构，将 Quad-Bayer 重新映射为标准 Bayer Pattern。

三、Pattern-Aware Remosaic

对于待恢复像素 (p)，可以从相同 Color Plane 的邻域中估计：

B^R(p)=∑q∈NR(p)w(p,q)Q(q)∑q∈NR(p)w(p,q)\hat B_R(p)= \frac{ \sum_{q\in N_R(p)} w(p,q)Q(q) }{ \sum_{q\in N_R(p)} w(p,q) } B^R​(p)=∑q∈NR​(p)​w(p,q)∑q∈NR​(p)​w(p,q)Q(q)​

其中：

  • (N_R(p)) 表示当前位置附近相同颜色的有效采样点；
  • (w(p,q)) 表示根据空间距离和局部结构计算得到的权重。

如果只进行简单均值插值，在文字、棋盘格、树叶等高频区域很容易产生：

False Color
Zipper Artifact
Edge Blur
Texture Loss

因此恢复过程中需要显式感知局部结构。

完整处理路径为：

Quad-Bayer RAW
        ↓
CFA Pattern Identification
        ↓
Pattern-Aware Remosaic
        ↓
Joint Denoise
        ↓
Standard Bayer RAW

当前平台已经能够对 Quad-Bayer 内置样例运行完整实验，并输出 RAW Preview、最终重建结果以及局部细节、ColorChecker 等对比结果。

四、真实 RAW 噪声不是简单高斯噪声

第二个实验关注真实手机 Camera 的 RAW Noise。

很多基础图像处理实验会直接加入固定方差的 Gaussian Noise：

y=x+ny=x+n y=x+n

但真实 Sensor Noise 通常具有明显的 Signal-Dependent 特征。

一个常用近似模型为：

σi2≈ayi+b\sigma_i^2 \approx ay_i+b σi2​≈ayi​+b

其中：

  • (ay_i)：主要对应与信号强度相关的 Shot Noise；
  • (b)：主要对应 Read Noise 等信号无关噪声。

因此：

RAW 图像不同位置的 Noise Level 本身就可能不同。

亮区、暗区不能简单使用完全相同的去噪强度。

五、Noise-Aware RAW Restoration

为了利用噪声统计特性，可以将恢复过程写成：

x^=======arg⁡min⁡x12∑i(xi−yi)2ayi+b+ε+λ∑iρδ(∣∇xi∣)\hat{x} ======= \arg\min_x \frac{1}{2} \sum_i \frac{(x_i-y_i)^2} {ay_i+b+\varepsilon} + \lambda \sum_i \rho_\delta(|\nabla x_i|) x^=======argxmin​21​i∑​ayi​+b+ε(xi​−yi​)2​+λi∑​ρδ​(∣∇xi​∣)

整个目标函数由两部分组成。

Noise-Aware Fidelity

(xi−yi)2ayi+b+ε\frac{(x_i-y_i)^2} {ay_i+b+\varepsilon} ayi​+b+ε(xi​−yi​)2​

传统 L2 Fidelity 默认所有像素具有相同噪声水平。

这里则根据当前像素估计的 Noise Variance 自适应调整权重。

噪声越大的区域，对观测 RAW 的信任程度越低；噪声较小的区域，则更多保留原始 Sensor 信息。

Huber-TV Regularization

空间约束采用：

λ∑iρδ(∣∇xi∣)\lambda\sum_i\rho_\delta(|\nabla x_i|) λi∑​ρδ​(∣∇xi​∣)

TV Regularization 可以抑制随机噪声，但纯 TV 容易造成 Staircase Artifact。

因此引入 Huber Loss，使小梯度区域保持平滑，同时减少对真实强边缘的过度惩罚。

最终希望实现三者之间的平衡：

Noise Suppression
        +
Edge Preservation
        +
Local Structure Preservation

六、基于 SIDD 的真实手机噪声实验

为了避免算法只在人工 Gaussian Noise 上有效，项目进一步使用 SIDD 真实手机噪声数据进行验证。

实验数据包含：

Noisy RAW
Ground Truth RAW
Metadata

恢复过程直接作用于 Bayer RAW，而不是先转换到 JPEG 后再进行去噪。

处理完成后统一生成：

Noisy

Ground Truth
Compare View

并计算：

因此算法效果可以同时从两个维度评价：

Subjective Image Quality
        +
Objective IQ Metrics

当前展示平台已经支持 SIDD 内置样例运行，并展示 Noisy、Denoised、GT 及 PSNR / SSIM 等结果。

七、统一到标准 Bayer RAW

Quad-Bayer Remosaic 和 RAW Denoise 本质上并不是两个孤立算法。

前者解决：

Sensor CFA 结构发生变化以后，如何重新得到标准 Bayer Sampling。

后者解决：

Bayer RAW 中存在真实 Sensor Noise 时，如何恢复更加可靠的像素值。

因此 OpenCameraIQ 将两条路径统一到 Standard Bayer RAW：

这个设计的重点在于：

图像恢复不是独立于 Camera Pipeline 存在，而是 ISP Pipeline 中的一个 Processing Block。

八、RAW Pipeline 中的 BLC

在 RAW Pipeline 中，Black Level Correction 通常是非常靠前的一步。

Sensor 即使没有实际光输入，也可能输出一个非零 Digital Value。

因此需要进行：

Icorrected====================clamp⁡(Iraw−B,0,W−B)I_{\text{corrected}} ==================== \operatorname{clamp} (I_{\text{raw}}-B,0,W-B) Icorrected​====================clamp(Iraw​−B,0,W−B)

随后归一化：

Inorm===============IcorrectedW−BI_{\text{norm}} =============== \frac{I_{\text{corrected}}} {W-B} Inorm​===============W−BIcorrected​​

其中：

  • (B)：Black Level；
  • (W)：White Level。

如果没有正确执行 BLC，后续很多模块都会受到影响，包括：

Demosaic
Noise Estimation
AWB
CCM
Tone Mapping

因此 OpenCameraIQ 的目标并不是直接在输入图像上调用一个算法，而是按照真实 Camera ISP 的顺序组织数据。

项目整体规划的 ISP 顺序为：

九、C++ ISP 工程架构

除了图像算法本身，我还希望把算法放进一个接近实际 Camera 工程的数据流中进行验证。

因此项目在 C++ 侧定义了统一的数据结构和 Pipeline Interface。

整体数据流：

Camera Source
      ↓
    Frame
      ↓
ISP Pipeline
      ↓
Frame Metrics
      ↓

其中 Camera Source 与上层 ISP 解耦。

当前使用 MockCamera 完成工程链路验证，后续可以替换为：

DngCamera
UsbCamera
LibcameraCamera
AndroidCamera

而上层 Frame、ISP Pipeline、Metrics 和调试 UI 不需要整体重写。

这也是项目在工程设计上比较核心的一点：

Camera 输入可以替换，但上层数据接口保持稳定。

项目当前已经完成 CMake + C++ Backend、MockCamera、Frame、CameraMetadata、IspPipeline、HTTP/WebSocket 与基础测试。

十、Web Tuning Console

为了避免图像算法变成“输入一张图，输出一张图”的黑盒实验，OpenCameraIQ 同时搭建了 Web Tuning Console。

这样每一个 ISP Block 都可以进一步分析：

  • 输入是什么；
  • 输出是什么；
  • 参数是什么；
  • 对画质有什么影响；
  • Runtime 是多少；
  • Failure Case 是什么。

项目本身也是按照“输入数据 → 算法处理 → 统计指标 → 可视化 → 参数调整 → 测试验证”的闭环进行组织。

也就是说，当前项目更强调：

当前 C++ 主链实际接入的是 MockCamera → IspPipeline，Quad-Bayer 和 SIDD 算法则复用已经验证过的独立实验流程，因此不会把尚未迁移到 C++ 的算法包装成已经完成的 C++ ISP 实现。

总结

OpenCameraIQ 最开始来源于两个 RAW 图像问题：

一个是：

Quad-Bayer 特殊采样结构应该如何恢复？

另一个是：

真实 Sensor Noise 应该如何建模和去除？

但随着实验继续推进，我发现单独讨论算法并不足以理解 Camera 图像处理。

真正完整的问题应该是：

Sensor 如何采样
        ↓
RAW 如何表示
        ↓
Metadata 如何影响处理
        ↓
ISP 如何组织算法
        ↓
图像质量如何评价
        ↓
算法如何调试和验证

因此最终将项目扩展为 OpenCameraIQ。

它并不是追求实现一个完整商业 Camera ISP，而是希望用一个规模可控的工程，把 RAW、ISP、图像恢复、Camera 数据流、IQ Metrics 和调试工具真正串起来。

相比单独实现某一个算法，这个项目更关注的是：

一个图像算法，如何从数学模型变成 Camera Pipeline 中可以解释、可以测试、可以评价、可以调试的工程模块。
