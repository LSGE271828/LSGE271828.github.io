DS Harness与BrowserSkill浏览器智能体联动

AI Agent工程实践-基于DeepSeek Harness与BrowserSkill构建浏览器智能体

实践背景

随着 AI Agent 技术改变着实践方式,在B站上也出现了很多不同的讨论和应用方案分享。

有一些用户认为，现在很多方案过于复杂，需要配置 MCP、额外安装浏览器环境，或者绑定特定框架，搭建成本比较高。他们提出，其实通过 Web Access 技能结合浏览器 CDP（Chrome DevTools Protocol），就可以直接让 AI 操作已有的浏览器，不需要重新部署一套环境，流程更加简单。同时，真实浏览器的优势在于可以实时看到 AI 的操作过程，遇到问题时也方便人工介入。

但也有部分用户认为，像 Playwright MCP 等方案同样成熟，在自动化控制方面具有较好的稳定性，只是需要额外进行配置。不同方案之间主要区别在于使用场景、扩展能力以及搭建复杂度。

基于这些讨论，我尝试采用 DeepSeek Harness 结合 BrowserSkill 的方式搭建浏览器智能体工作流，通过加载浏览器操作技能，使 AI Agent 能够调用 CDP 控制真实浏览器，并完成网页访问、信息交互以及表格等任务。通过实际搭建和测试，探索一种更加简单、灵活的浏览器智能体实现方式。同时，也结合 Cordis 等浏览器插件扩展方案。

一、从LLM到Browser Agent的需求分析

1.1 普通大模型的限制

传统LLM工作方式：

用户输入

↓

模型推理

↓

文本输出

模型并没有真正改变外部环境。

例如用户：

"帮我完成一个网页任务。"

普通模型只能告诉用户：

"你可以点击这里，然后输入......"

但是无法真正执行。

Browser Agent希望实现：

用户目标

↓

Agent理解任务

↓

打开浏览器

↓

观察网页

↓

执行操作

↓

完成任务

这意味着AI从回答者变成执行者。

1.2 为什么选择浏览器作为入口

浏览器是现代计算环境中最通用的软件入口。

大量系统：

  • 企业后台；
  • 管理系统；
  • 在线服务；
  • 数据平台；

都运行在浏览器中。

如果AI能够控制浏览器，就相当于获得了一种通用计算机操作能力。

因此浏览器Agent成为Computer Use方向的重要组成。

二、传统浏览器自动化技术分析

2.1 Selenium时代

Selenium是最早广泛应用的网页自动化框架之一。

它通过WebDriver控制浏览器。

结构：

Python脚本

↓

Selenium WebDriver

↓

ChromeDriver

↓

Chrome

优势：

  • 成熟；
  • 稳定；
  • 生态丰富。

但是问题：

它依赖人工编写流程。

例如：

find_element()

click()

send_keys()

开发人员必须提前知道页面结构。

这适合测试。

但是不适合作为通用Agent。

2.2 Playwright时代

Playwright进一步提升了浏览器自动化体验。

优势：

  • 多浏览器支持；
  • 自动等待；
  • 更强定位能力；
  • 更好的调试能力。

结构：

Agent

↓

Playwright

↓

↓

Web Page

但是默认情况下：

Playwright通常创建新的浏览器环境。

例如：

新的Cookie

新的Profile

新的登录状态

对于自动化测试很好。

但是对于个人AI助手：

用户希望：

"继续使用我已经登录的浏览器"

这时体验下降。

三、Chrome CDP探索过程

3.1 CDP介绍

Chrome DevTools Protocol是Chrome提供的远程控制协议。

启动：

chrome.exe --remote-debugging-port=9222 --user-data-dir=C:\chrome-agent

Chrome开放：

localhost:9222

访问：

http://localhost:9222/json

可以获得：

  • 页面列表；
  • WebSocket地址；
  • 调试入口。

3.2 CDP优势

最大的优势：

控制真实浏览器。

因此：

用户可以：

  • 看见AI操作；
  • 手动接管；
  • 保留登录状态。

这也是很多个人Agent方案喜欢CDP的重要原因。

3.3 CDP不足

CDP只是控制协议。

它提供：

click
type
evaluate
screenshot

但是没有：

这个按钮是什么意义？
下一步应该做什么？

因此需要更高层Agent框架。

十四、从自动化脚本到智能体系统：技术路线演进分析

14.1 自动化工具的发展过程

浏览器自动化并不是一个新概念。

早期网页自动化主要解决的是：

让程序代替人工重复点击网页。

例如：

  • 自动登录；
  • 自动提交表单；
  • 自动抓取数据。

这一阶段的核心思想：

人提前设计流程

↓

程序严格执行

因此自动化系统通常具有明确的输入和输出。

例如：

if 找到按钮:
    click()

else:
    error

这种模式非常稳定，但是缺少智能。

14.2 为什么传统自动化无法直接升级为Agent

很多人认为：

"给Playwright接一个大模型，就是Agent。"

实际上并不是。

原因在于：

浏览器控制只是执行能力。

真正的Agent还需要：

目标理解

例如：

用户说：

帮我完成网页测试。

模型需要理解：

  • 测试目标是什么；
  • 哪些步骤重要；
  • 什么结果代表完成。

环境感知

Agent需要知道：

当前页面是什么状态。

例如：

当前页面：

登录页面

下一步：

输入账号

当前页面：

验证码页面

下一步：

请求人工帮助

动态规划

网页不是固定环境。

可能出现：

  • 弹窗；
  • 网络错误；
  • 页面变化；
  • 权限限制。

因此Agent需要：

观察结果。

重新规划。

继续执行。

这也是BrowserSkill加入页面观察能力的重要原因。

  • Session管理；
  • 状态维护。

一个独立浏览器任务上下文。

购物网站

企业后台

可以使用不同Session。

优势：

  • 状态隔离；
  • 避免任务冲突；
  • 方便管理。

  • 页面DOM；
  • 浏览器事件；
  • 当前标签页。

button

input

信息采集

提供：

  • 页面结构；
  • 可访问性信息；
  • 视觉信息。

帮助Agent理解页面。

十八、为什么Agent Window比无头浏览器更适合个人AI助手

无头浏览器：

后台运行

用户不可见

适合：

自动测试。

但是个人AI助手更需要：

透明执行

用户可以：

  • 看AI做什么；
  • 随时暂停；
  • 手动修改。

因此：

Agent Window更符合Human-in-the-loop设计。

二十五、为什么没有直接采用CDP最终方案

虽然CDP成功，但是继续分析发现：

它解决的是：

浏览器控制问题

不是：

Agent理解问题

例如：

CDP可以执行：

document.querySelector("#button").click()

但是它不知道：

这个按钮是不是用户需要点击的。

因此：

CDP适合作为底层能力。

不适合作为完整Agent框架。

企业自动化。

Browser Use

特点：

  • 强调网页Agent；
  • 提供任务规划。

适合：

研究Agent逻辑。

BrowserSkill

特点：

  • 面向Agent设计；

  • 有CLI；
  • 有Session；
  • 有语义观察。

最终选择：

BrowserSkill。

二十七、BrowserSkill安装过程详细记录

27.1 Git获取源码

执行：

git clone https://github.com/Tencent/BrowserSkill.git

遇到：

Failed to connect to 127.0.0.1 port 7890

原因：

Git配置了代理。

解决：

git config --global --unset http.proxy

git config --global --unset https.proxy

重新clone成功。

27.2 安装Rust

最初尝试：

winget install Rustlang.Rustup

发现：

winget not recognized

说明当前Windows环境没有winget。

随后采用：

Invoke-WebRequest https://win.rustup.rs -OutFile rustup-init.exe

安装Rust。

验证：

rustc --version

成功。
